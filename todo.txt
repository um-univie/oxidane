[x] Make SMILESParser reusable / reduce allocations. DONE, but the premise was
   wrong and the measurement is the useful part.
   Added `SMILESParser::reset`, which empties every buffer in place instead of
   replacing the whole parser at each `.` (that dropped the atom, bond and ring
   tables and rebuilt them from nothing), and a capacity reserve for the atom
   and bond vectors sized from the input length.
   Raw parse 8.3 -> 7.6us per molecule, end-to-end 19.6 -> 18.4us (min of 6),
   about 6%. `reset` itself shows nothing on the benchmark corpus because those
   SMILES are single-fragment, so the path never runs; it is correct rather
   than measurable there.
   WHERE THE TIME ACTUALLY GOES (examples/parse_split.rs):
       raw, tokenise + build graph          8.3us
       + hydrogens, chirality, CIP refs     9.0us     (those three cost 0.7us)
       + aromaticity perception            19.5us     (perception costs 10.5us)
   So aromaticity perception is 54% of a default parse, and parser allocation
   was never the lever. 72 of the 73 benchmark molecules contain a ring and 71
   of those are written Kekule, so every one pays for perception -- which is
   the cost of making `C1=CC=CC=C1` and `c1ccccc1` answer the same questions.
   The early-out for acyclic molecules already exists. Making this cheaper
   means making `aromatize` itself cheaper, which is its own piece of work.

[x] DECIDED: the convention for a THREE-coordinate stereocentre whose hydrogen
   is written inside the brackets, e.g. C[P@@H]C1CCCCC1. We keep ours.
   OpenSMILES defines the bracketed hydrogen's position only for four-neighbour
   centres; it never mentions lone pairs, so for three-coordinate centres there
   is nothing to be conformant to and RDKit parity is not an argument either
   way. What decides it is that our reading is self-consistent and RDKit's is
   not: RDKit gives `C[P@@H]X` and `C[P@@]([H])X` -- the same molecule --
   opposite descriptors, because it orders the bracketed hydrogen last when the
   centre has three neighbours but at its written position when it has four.
   Verified over P, As, S and N three-coordinate centres plus four-coordinate
   controls: implicit and explicit spellings agree 8/8 on the descriptor and
   8/8 on the canonical form, and 256 renumberings produced no failures.
   Costs 2 of 383 in the CIP differential against RDKit; that is the price and
   it is documented in cip_tests' module docs and in
   notes/rdkit-divergences.md.
   Pinned by cip_tests::implicit_and_explicit_hydrogen_agree and by the
   three-coordinate entries in descriptors_are_invariant_under_atom_renumbering.

[x] CIP for allene (AL) axial chirality. DONE, third attempt, after the first
   two established that the blocker was AL having no carrier reference at all.
   Three pieces, which had to land together because the first changes what the
   stored tag means:
     1. `chirality::index_sorted_allene_carriers` defines the reference -- the
        two ends by atom index, and within each end its substituents by atom
        index -- and `cip::normalize_allene_references` re-expresses a freshly
        parsed tag from the SMILES written order onto it, mirroring what
        normalize_tetrahedral_references does for TH.
     2. `reorder_molecule` remaps AL against those four carriers instead of
        against the centre's own two neighbours, which could not encode a
        four-element winding.
     3. `to_smiles` re-derives the tag from the emission order. The writer is
        single-pass and has the node of neither end at the centre -- one is its
        parent, the other its child -- so `allene_emission_orders` walks the
        tree once beforehand and hands the result down, the way ring closures
        and directional marks already are.
   The CIP config then ranks the carriers WITHIN each end rather than over all
   four, which is the proximity rule axial chirality requires: without it
   2,3-pentadiene has no descriptor, its two methyls being indistinguishable
   from each other and likewise its hydrogens, and it is a textbook chiral
   allene.
   Verification, since RDKit is not usable here -- `MolToSmiles` drops allene
   stereochemistry outright:
     - Round-trip stable for six allenes including one written from the centre.
     - 0 drift in 96 random renumberings of the canonical form, and 0 failures
       in 120 renumberings of the CIP descriptors.
     - Descriptors hand-derived from the OpenSMILES rule for two independent
       cases, both matching.
     - The same allene written from either end gives the same descriptor, as
       the even-permutation argument requires.
   Fixed two tests that had been asserting the old, meaningless behaviour:
   `invariance_allene` listed three SMILES as the same molecule when two of
   them are its enantiomer (each transposes one end's substituents while
   keeping the tag), and `allene_chirality_update` expected a tag not to change
   when two of its carriers swapped indices.
   Tests: cip_tests::{allenes_are_labelled, an_allene_reads_the_same_from_either_end,
   an_allene_with_a_symmetric_end_has_no_descriptor}, plus allene entries in
   descriptors_are_invariant_under_atom_renumbering, and
   chiral_canonization_tests::{invariance_allene, discriminate_allene_enantiomers}.

[x] SDF/MOL property blocks were collected as raw strings and never
   interpreted. DONE. `M  CHG`, `M  RAD` and `M  ISO` are now parsed into
   `MOLFile::{charges,radicals,isotopes}`; everything else still lands in
   `properties` verbatim. Each block is `Option`, because the format says these
   lines supersede the atom block outright rather than adding to it -- a
   present-but-empty block has to zero the atom block's values while an absent
   one must leave them alone, and files routinely write both, the atom block
   entries being there for readers too old to know the property lines.
   Three separate bugs came out of it, none of which any test could have hit,
   because no SDF in tests/ carries a property line other than `M  END`:
     1. THE FIRST PROPERTY LINE WAS DROPPED. The state machine moved into its
        Properties state on the line it failed to read as a bond and only
        recorded lines from the next one on. In a real file that first line is
        the `M  CHG`, so precisely the line that mattered was the one lost.
     2. THE ATOM BLOCK CHARGE COLUMN IS A CODE, NOT A CHARGE. 1..3 mean +3..+1
        and 5..7 mean -1..-3, with 4 meaning doublet radical. We stored the raw
        code as the charge, so every charged atom in every SDF was wrong -- a
        +1 nitrogen read back as +3 and a -1 oxygen as +5, which is not a
        charge a second-row element can carry.
     3. THE MASS DIFFERENCE COLUMN NEEDED A TABLE WE DID NOT HAVE. It counts
        from the most abundant isotope, and `chemistry_consts`'
        MONOISOTOPIC_MASSES holds the LIGHTEST one despite the name (see the
        open item below), so a local mass-number table lives in molfile.rs.
   Verified against RDKit with notes/sdf_property_oracle.py and
   examples/sdf_property_diff.rs in three modes: RDKit's own molblocks 30/30,
   the same molecules rewritten in the old atom block style 24/24, and an
   exhaustive sweep of every element against every charge code and every legal
   mass difference 2945/3540. All 595 sweep divergences are RDKit losing
   information, not us: 590 are it discarding charge code 4 outright (a carbon
   written as a methyl radical comes back as methane, silently), 6 are it
   storing an impossible mass number as an unsigned underflow (65534). Both
   are written up as rdkit-divergences.md §1.2 and §1.3.
   Tests: sdf_tests::property_block, 13 of them.
   NOT DONE, because there is nothing to do it to: there is no SDF/MOL writer
   in the crate, so this is a read path only and there is no round trip to
   test. If a writer is added it has to emit `M  CHG`/`M  RAD`/`M  ISO` rather
   than the atom block columns, which cannot represent charges beyond +-3 or
   isotopes outside -3..+4 of the common mass.

[x] chemistry_consts had three separate bugs in its isotope data. FIXED AT THE
   SOURCE, in ../chemistry_consts/src/consts.rs, bumped 0.2.0 -> 0.3.0 because
   it changes every exact mass the crate reports. molecules carries no
   workaround for any of it.
     1. MONOISOTOPIC_MASSES held each element's LIGHTEST isotope, not its most
        abundant one, for 39 elements: He 3.016 (helium-3, abundance 0.0001%)
        rather than 4.003, Li 6.015 rather than 7.016, Fe 53.940 rather than
        55.935. Both values are plausible masses for the element, which is why
        it went unnoticed. FIX: the array is now derived from ISOTOPES with a
        const fn instead of being a second hand-maintained copy of the same
        fact. That is the actual root cause -- two tables, one authoritative,
        no link between them -- so the drift is now impossible rather than
        merely corrected.
     2. ISOTOPES had thorium and uranium CORRUPT: each carried a leading entry
        whose abundance field held the element's standard atomic weight
        (232.0377, 238.02891) paired with a non-dominant nuclide. The table is
        sorted by decreasing abundance, so a "232" sorted ahead of a real 1.0
        and every reader of entry 0 got Th-230 and U-233 instead of Th-232
        (100% of natural thorium) and U-238 (99.27%).
     3. `most_abundant_isotope()` returned `isotope.mass as u16`, truncating
        where a nucleon count has to round. The mass defect puts nearly every
        nuclide just under its integer, so it was wrong for 74 of the 84
        elements it can answer for -- oxygen returned 15, fluorine 18. It was
        right for hydrogen and carbon, which is presumably how it survived.
   Also aligned Tc/Rn/Ra/Np/Pu onto the IUPAC conventional nuclide, which is
   the one the crate's own STANDARD_ATOMIC_WEIGHTS already named; radon had
   said Rn-211 in one table and Rn-222 in the other.
   Added the crate's first tests, 11 of them, all invariants rather than
   value checks: tables all indexed by atomic number, symbols round-trip,
   ISOTOPES sorted by decreasing abundance, abundances are fractions summing
   to at most 1 (this is what catches bug 2 exactly), nuclide masses near a
   whole number of nucleons and never fewer than the proton count,
   MONOISOTOPIC_MASSES equal to its ISOTOPES entry (bug 1), mass numbers equal
   to the rounded mass (bug 3), and the two mass tables naming one nuclide per
   unstable element. A reference crate with no tests is how all three of these
   lasted; the invariants are cheap and would have caught each one.
   KNOWN AND DELIBERATE: Bh, Hs, Mt and Rg keep their pre-existing reference
   nuclides. They have no standard atomic weight to arbitrate and their
   longest-lived nuclide is contested in the primary literature, so picking
   RDKit's numbers would be copying, not verifying. Documented as
   rdkit-divergences.md 3.2.

[x] SDF/MOL read path derived nothing the format leaves implicit. DONE.
   The block states which atoms are bonded to which; the hydrogens, the
   aromaticity and the stereochemistry are all derived, exactly as for a
   SMILES, and `from_sdf` derived none of them -- it built the graph and
   stopped, while the SMILES path runs four more steps. Alanine read back as a
   bare C3NO2 skeleton with no hydrogen anywhere, benzene had no aromatic bond,
   and of 1501 stereoisomers not one kept its configuration.
   Added `SdfParseOptions { hydrogens, stereochemistry, aromaticity }`,
   defaults matching SmilesParseOptions, with `from_sdf_with` /
   `from_sdf_entries_with`. Six real bugs came out of it:
     1. BOND LINES WERE SPLIT ON WHITESPACE. The bond block is fixed columns
        three wide with no separator, so past ninety-nine atoms the two indices
        run together -- a bond between 100 and 101 is `100101  1  0`. The
        connection table came apart entirely: a 116-atom peptide read back as a
        heap of loose methanes. Peptides and natural products are ordinary.
     2. `add_atom` DID NOT EXTEND `positions` OR `isotopes`. The trait default
        knows only the fields every representation shares, and `Molecule3D`
        indexes `positions` directly, so adding hydrogens gave twelve atoms and
        six positions and the next question about a distance panicked. Added
        `push_atom_extras`/`pop_atom_extras`/`remove_atom_extras` hooks, used by
        Molecule3D for `positions` and MolecularGraph for `partial_charges`,
        and handled `isotopes` in the defaults. Deleted Molecule3D's inherent
        `add_atom`, which shadowed nothing useful and never wired the reverse
        half of a bond.
     3. `determine_cis_trans_chirality` WROTE THE TETRAHEDRAL CLASSES.
        `Clockwise`/`Counterclockwise` instead of the CisTrans ones, so
        `C/C=C/C` came back as `C[C@@H]=[C@@H]C` -- stereocentres invented on
        atoms that are not stereocentres. It also shared one frame between two
        ends that are mirror images, and keyed on whichever neighbour each end
        happened to list first, so the answer moved with bond build order.
        Rewritten onto the convention `convert_directional_bonds_to_chiral`
        fixes. This was wrong for 3D files too, not just the new path.
     4. A LONE HYDROGEN VANISHED FROM `to_smiles`. Hydrogens fold into their
        neighbour's H count, unconditionally on the element, so one with no
        heavy neighbour folded into nothing: `[Cl-].[H+]` came out `[Cl-].`
        and `[H][H]` came out empty. Now folds only with a heavy neighbour and
        no charge, isotope or radical to carry.
     5. THE ATOM BLOCK VALENCE COLUMN WAS IGNORED. It is how a file says "this
        one takes no hydrogen": 15 for zero valence on a bare potassium, 3 on a
        germanium bonded to three ethyls. Added
        `add_hydrogens_with_valences`.
     6. 2D DEPICTIONS WERE FED TO THE 3D PERCEPTION. Every atom in a flat
        drawing is coplanar with its neighbours, so each four-coordinate one
        came back square planar and a drawn neopentane wrote out as `[C@SP3]`.
        The flat path now does only what a flat drawing can say.
   Stereochemistry: cis/trans from the coordinates, tetrahedral from the wedge
   column made pseudo-3D. Stereo code 3 ("either") is honoured on both paths --
   `tests/pentene.sdf` marks its double bond 3 while carrying 3D coordinates
